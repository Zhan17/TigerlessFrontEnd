## 加分与自主选择

- PDF 明确加分：画板之间及之外的优雅适配，并能解释实现方式。两个画板宽度之外只要求布局完整，不要求逐像素还原。
- PDF 自主项：tokens、图片和图标处理、状态管理、路由、API 契约及数据层、代码目录、组件和状态划分。
- 项目建议：语义化 HTML、键盘操作、可见焦点、减少动态效果偏好；这些是实现质量考虑，不伪装成 PDF 单独列出的额外条款。
- 非当前硬性要求：双模型协作、某种固定目录、固定测试覆盖率、线上部署、数据库、真实后端、完整登录/支付/问诊流程。
- PDF 要 GitHub 仓库链接，未明确规定仓库必须公开；用户希望最终公开，这是用户目标，单独记录。
- PDF 没有提供截止日期、工时或固定区块数量。

## 验证方式的实际边界

- 375 / 1440 做视觉对比；320–1920 做布局完整性巡检。只检查两个画板不足以证明 R05。
- 建议额外抽查 320、390、768、1024、1920，以及实际断点前后各 1px；连续拖动窗口仍需执行。这些检查点可调整，不是新增要求。
- 页面根节点禁止意外横向滚动；设计本来要求的局部轮播/裁切应控制在局部容器，不能用全局隐藏溢出来掩盖布局问题。
- “构建通过”不能替代视觉、交互和 Storybook 检查。未执行的检查写“未执行”，不要写通过。
- 先定义组件状态集合，再与 stories 对照；hover / focus / pressed 不能只靠使用者临时操作却没有可复现的展示方式。
