# Decisions

更新：2026-10-01。这里只记录会影响架构、验收、设计偏差或交接的重要取舍；普通样式修正和局部重构直接做即可。

## D01：五份工作文档 + 提交 README

- 状态：已采用。
- Decision：保留 requirements、design、architecture、decisions；合并 Task 与 Handoff 为 tasks-handoff；README 面向验收者。
- Why：需求、设计证据、结构理由、重要取舍和当前状态各有一个归属；减少重复更新。
- 未采用：六份工作文档另加独立 review-priority 和 deviation 文件。
- Reason to reject：任务状态与交接容易冲突；Review Priority 只需一节；偏差作业明确要求写 README。
- 重新考虑条件：真实交接积累到难以阅读时再拆分；不是因为以后“可能用到”而先扩张。

## D02：文档是上下文，不是审批流程

- 状态：已采用。
- Decision：明确分开作业硬性要求、已落地决策、建议、待验证；代码变化后修订建议。
- Why：用户希望记录上下文，但不希望文档成为开发负担。
- 未采用：把全部 SOP、固定阶段、固定断点和所有目录变成强制规则。
- Reason to reject：当前任务小，设计尚未核实，过早冻结会增加返工和维护量。
- 更新时机：任务完成/暂停/交接时更新状态；重要取舍时追加 decision；实施设计修正或自设计交互时更新 README。不要求每轮对话更新所有文件。
- 当前不创建长篇 AGENTS.md / CLAUDE.md。若后来确有双工具需要，可添加很短的入口，只指向这些文件并写少量真实规则。

## D03：Codex / Claude Code 可选串行协作

- 状态：轻量建议；Claude Code 尚未用于本轮。
- Decision：默认一个执行者负责当前任务；有必要时另一个模型针对风险点复核，再由当前执行者落实。用户决定采用哪些工具。
- Why：交接有价值，但第二模型不是完成作业的前提。共用源码、Git 和状态文件，比复制两套计划可靠。
- 未采用：两模型轮流重写同一区块、每一步强制双审、同时修改同一批文件。
- Reason to reject：增加冲突、上下文重复和时间成本；不能用模型互相同意替代实测。
- 适用复核点：数据契约、Hero 中间宽度布局、复杂交互、Storybook 状态覆盖、最终验收缺口。

推荐流程：

1. 接手者读 requirements、tasks-handoff，再按任务读设计/架构/决策及相关代码。
2. 查看 `git status`、分支、最近提交和未提交 diff；已有改动不假定可丢弃。
3. 明确本次任务、输入证据、完成条件；同一工作区同一批文件保持一个写入者。
4. 执行并记录真实验证结果；必要时把具体 diff、截图和疑问交给第二模型复核。
5. 收尾更新 Done / In Progress / Next 和短交接；保存各工具的完整原始日志及实际贡献。

这一流程不固定谁“更擅长”设计或代码，也不要求每次换工具都新开分支。

## D04：架构建议尚未冻结

- 状态：草案，见 [architecture.md](architecture.md)。
- 建议：单页组合 + ui/sections + types/mock + 简单数据入口。
- Why：让评审能先看类型，再追踪数据与组件；符合当前单页范围。
- 替代方案：所有内容放 page.tsx；完整 feature/domain/repository 多层结构。
- 暂不选原因：前者难审阅类型与组件；后者目前缺少复杂度依据。这是设计推演，尚未通过真实代码验证。
- 成为已采用的条件：完成设计盘点、脚手架和首个端到端区块后，按实际代码修订。

## D05：Hero layout 留待证据确定

- 状态：待验证，尚无布局实现。
- 待解决：字体、标题换行、胶囊和分类卡的尺寸/顺序、移动与桌面关系。
- 当前倾向：文档流 + flex/grid；只对有依据的装饰局部定位。
- 替代方案：整个 Hero 按桌面坐标绝对定位；整个区块按比例缩放。
- 倾向不选原因：320–1920 中间宽度、文本换行和触达尺寸可能不稳定；尚未做实际比较，不记为已验证 rejection。
- 拍板证据：375 / 1440 的 Hero 节点与截图、所用素材、至少一次中间宽度和断点附近验证。
- 最终记录：选择了什么、为什么、未选方案的具体风险、代码位置和验证证据。

## 需要时使用的记录格式

`ID / 状态（建议、已采用、被替代） / 问题与证据 / Decision / Why / Alternatives & rejection reason / 验证 / 重新考虑条件`。

没有实际评估过的方案写“备选/待比较”，不要虚构 rejected 记录。已采用的重要决策被替代时，保留原条目并链接新条目；普通临时想法可以删改。

设计偏差和自设计交互的提交日志直接写 [README](../README.md)，这里只在有重要取舍时引用对应 ID。
